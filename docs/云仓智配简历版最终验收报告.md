# 云仓智配简历版最终验收报告

验收日期：2026-09-29。范围：不改变 V1 OpenAPI 和库存核心事务，新增可选 V1.1 创建请求幂等及低库存异步通知，并对既有 Redis 缓存做真实环境验证。实施前基线见 `简历升级差距矩阵.md`。

## 1. 当前技术栈和真实功能

Java 17、Spring Boot 3.5、MyBatis、MySQL 8/InnoDB、Redis、RabbitMQ、JUnit 5。V1 50 个 HTTP 操作覆盖入库、出库预占与释放、跨仓调拨、盘点、库存流水和同步库存预警。Redis 只缓存单仓单 SKU 库存详情；RabbitMQ 只异步投递预警通知。Vue 后台仍按 V1 页面运行，V1.1 通知通过 API 查询。

## 2. MySQL 并发证明

本轮在本机 MySQL 8.0.45 / InnoDB、独立 `yuncang_acceptance_*` 数据库重跑 `MySqlInnoDbAcceptanceTest`：13/13 PASS。包含同单双线程 reserve、两个订单争抢 10 件库存分别要 7 件、首次库存行并发 upsert、多 SKU 整单回滚、状态机、流水和预警一致性。每次脚本建临时数据库、导入正式 V1 SQL、测试后删除。库存主流程仍采用事务、行锁、条件更新和唯一约束；无 Redis 扣库存或 MQ 异步扣库存。

## 3. Redis 真实测试

使用虚拟机 Redis 7.0.15 的独立逻辑库 15 与本机 MySQL 8，`RedisAcceptanceTest` 5/5 PASS。覆盖 miss/hit、TTL 与随机抖动、过期回源、提交后缓存失效及版本代数、回滚不污染缓存、并发旧读回填、不存在库存行的零库存语义和首次入库可见。`RedisUnavailableAcceptanceTest` 1/1 PASS：模拟连接拒绝，查询回源 MySQL，入出库写事务仍提交。未停止共享虚拟机 Redis 服务。未增加空值缓存、仓库或 SKU 基础资料缓存，简历不得写这三项。Redis 缓存失效失败可能在 TTL 内短暂读到旧值，扣减仍由 MySQL 保证。

## 4. 请求级幂等

`Idempotency-Key` 是四个创建接口的可选请求头。`CreateRequestIdempotencyService` 在一个 MySQL 事务中插入唯一请求键、创建业务单、写回业务 ID；重复键通过 `SELECT ... FOR UPDATE` 读取已提交单据。相同键不同 JSON 请求体返回 409。`IdempotencyIntegrationTest` 在真实 MySQL 上 4/4 PASS，覆盖双线程同键建出库单只生成一张、请求体冲突、用户作用域、失败回滚、调拨/盘点重放及实际 HTTP 请求头。无键仍按 V1 建单。此能力解决创建请求网络重试；动作接口的重复库存副作用由原有状态机解决，两者不可混称。

## 5. RabbitMQ / Outbox / 消费幂等

虚拟机 RabbitMQ 4.3.6，独立验收交换机与队列。`RabbitMqAcceptanceTest` 2/2 PASS：ACTIVE 预警写 Outbox、Publisher Confirm 后 SENT、消费者生成可通过 V1.1 API 查看的一条 LOW_STOCK 通知、恢复后 STOCK_RECOVERED 通知、同 eventId 重投只一条、消费者停启后积压消息可处理、mandatory Return 检出不可路由消息、畸形消息进入死信队列、发送端连接拒绝时保留 PENDING 并在连接恢复后重试成功。`OutboxIntegrationTest` 1/1 PASS：库存、预警和 Outbox 插入在故意业务异常后一起回滚。验收测试清理自己的交换机和队列，不改共享 Broker 配置。

Outbox 解决 MySQL 提交后、MQ 尚未发送时的交接窗口；它不是 MySQL 与 RabbitMQ 的原子提交。Publisher Confirm 表示 Broker 确认接收，Return 表示消息无法路由，消费者可能重复处理，因此 `notification.event_id` 使用数据库唯一约束。发布后写 SENT 失败时会重发，由消费幂等兜底。死信消息目前需人工重投；没有自动通知投递时限或短信/邮件通道。

```powershell

./scripts/run-mysql-acceptance.ps1 -TestPattern 'IdempotencyIntegrationTest' -IncludeUpgradeSchema
```

## 8. 尚存可靠性边界

- **中**：死信队列需要人工排查和重投，尚无运营告警与自动重放。Outbox PENDING 会持续按固定间隔重试，未设置退避和过期治理。
- **中**：Redis 缓存删除/版本更新失败时可短时返回旧详情，最长受 TTL 约束；库存写事务不依赖缓存。
- **中**：通知是共享列表，现有系统没有仓库级授权或个人已读状态；若用于真实多租户环境需要补权限模型。
- **低**：`Idempotency-Key` 不传时创建请求仍可能因网络重试重复建单；这是兼容 V1 的既定边界。
- **低**：未做负载压测，不能声称吞吐或性能提升幅度。

## 9. 面试解释与不能写的点

最值得讲的 5 点：三量库存如何保持不变量；条件更新、行锁、状态机各解决什么竞争；多 SKU 失败为何整单回滚；请求幂等键与动作级状态幂等的区别；Outbox、Confirm/Return、消费唯一键如何覆盖不同故障窗口。不能写 Redis 主库存、Lua/Redisson 防超卖、MQ 扣库存、缓存空值防穿透、SKU/仓库资料缓存、消息 exactly once、完全自动恢复死信、百万并发或未经测量的性能数字。
