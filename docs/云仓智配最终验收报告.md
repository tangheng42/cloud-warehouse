# 云仓智配最终验收报告

验收日期：2026-09-28。基线：`yuncang-openapi.yaml`、`V1.0-项目设计.md`、`docs/sql`、源码与现有测试。验收按“契约 → 设计 → 数据库约束 → 源码”核对。此报告把**源码审查与 H2 测试通过**和**真实基础设施运行验证**分开记录。

| 主题 | OpenAPI 契约 | 原设计文档 | 数据库 SQL | 验收前源码 / 本次处理 |
|---|---|---|---|---|

## 1. V1 接口完成度

契约 50 个 operation、40 个路径；已实现 50、缺失 0、发现的方法/路径不一致 0。动态路由集合测试通过。逐项 Controller/Service/Mapper 与测试证据见 [接口验收矩阵](V1.0-接口验收矩阵.md)。角色、DTO/VO、错误码、状态前置条件、库存影响和流水已按源码与核心测试审查；未建立全部 50 项的逐字段自动回归，不将其称为百分百自动验证。

## 2. 核心业务正确性

| 业务 | 审查结果 |
|---|---|
| 入库 | PENDING 确认后 physical/available +q，写 INBOUND；重复确认返回状态冲突。首次库存行由唯一键 upsert 创建。 |
| 出库 | reserve、release、confirm 和两种 cancel 分支对应三量变化及 OUTBOUND_LOCK/RELEASE/OUTBOUND；库存扣减使用条件 UPDATE。 |
| 调拨 | reserve/release 在源仓，dispatch 源仓出仓形成在途，receive 目标仓入仓；目标仓首次 SKU 使用 upsert。IN_TRANSIT 不能取消。 |
| 盘点 | 创建时保存三项快照与实盘数；确认要求快照仍一致、实盘数不低于 locked；按 delta 同调 physical/available，delta=0 不写流水。 |
| 不变量 | SQL CHECK 限制三量非负且 physical=available+locked；扣减型 UPDATE 有可用量/锁定量条件。 |
| 预警 | 每仓每 SKU 唯一；低于安全库存 ACTIVE，恢复 RESOLVED；库存动作及 SKU 安全库存修改在同一事务内刷新。 |

## 3. 事务设计

库存动作在 Service 事务中同时处理单据状态、库存、流水和预警。新增三 SKU 第三行不足测试验证前两行库存及流水回滚，单据仍为 CREATED。异常不留半张单。Redis 失效安排在数据库提交后，不参与 MySQL 原子事务。

## 4. 并发控制

单据动作先 `SELECT ... FOR UPDATE` 并检查状态；明细按 SKU ID 顺序处理；库存使用条件 UPDATE；首次库存行依赖 `(warehouse_id, sku_id)` 唯一约束。新增真实双线程测试：同单并发预占仅一次成功；两单争抢同一 SKU（库存 10，各需 7）至多一单成功，没有负库存。测试环境为 H2 MySQL 模式，尚需真实 MySQL 压力验证。数据库死锁仍可发生，接口以可重试业务错误反馈。

## 5. 幂等设计

动作接口通过行锁、状态检查及条件 UPDATE 实现**无重复库存副作用**；重复请求一般返回 `ORDER_STATE_CONFLICT`，不是“返回第一次成功响应”的请求级幂等。契约没有 Idempotency-Key，因此未增加协议字段。库存流水没有业务单据加类型唯一键，因为合法的重复 reserve/release 周期会产生同类型流水。

## 6. Redis

默认关闭；开启后只缓存单仓单 SKU 库存详情。Cache Aside、5 分钟基础 TTL 加 30 秒随机抖动（均可配置），事务提交后提升版本键并删旧值，防止旧读回填当前版本。故障回源 MySQL。不存在行暂不缓存：其零库存语义依赖仓库/SKU 校验，且安全库存变更无法枚举并清理所有不存在组合。**限制：** Redis 失效失败可能让旧值保持到 TTL；版本元数据键无 TTL，会随查询过的仓库/SKU 组合增长；未在真实 Redis 上跑集成测试。库存写入与并发控制完全留在 MySQL。

## 7. RabbitMQ

未接入。项目目前没有邮件、站内信等真实非核心通知接收端；现有预警必须随库存事务同步一致。仅为增加技术栈而发送后打印日志或异步重算预警没有业务收益。将来有真实异步通知时，可在提交后发库存变化事件；消费者必须按事件唯一 ID 去重，若要求数据库提交后消息可靠必达，还需评估 outbox。当前不宣称实现 RabbitMQ。Lua、Redisson 也未加入：当前行锁、条件更新、唯一约束及事务足以保护单体 MySQL 库存；只有出现跨系统共享锁或真实 Redis 原子多键写入需求，才重新评估。

## 8. 数据库与索引

检查了 15 张表、Mapper XML 的筛选与排序；没有无证据添加索引。下表为主要命中路径。组合筛选可利用左前缀；实际执行计划仍需在目标 MySQL 数据量上用 EXPLAIN 验证。

| SQL / 查询 | WHERE / ORDER BY | 现有索引 | 原因与边界 |
|---|---|---|---|
| `StockMapper.findByWarehouseAndSku` | warehouse_id + sku_id | `uk_warehouse_sku` | 单条库存唯一定位和首次行并发创建。 |
| `StockMapper.listBySku` | sku_id；warehouse_id 排序 | `idx_warehouse_stock_sku` | 安全库存调整按 SKU 扫描；排序可能额外处理。 |
| 四类单据 `list` | warehouse/source/target、status、created_at/id DESC | 对应 `*_warehouse_status_created`、`transfer_*_status_created`，另有 status/created 索引 | 覆盖常用筛选组合；未指定可选条件时可能走 created 索引。 |
| 四类单据批量明细 | order_id IN (...)；order_id,id | 明细表 `uk_order_sku` 的 order_id 前缀 | 一页一次批量取明细；`id` 排序未必完全覆盖。 |
| `StockFlowMapper.list` | biz_type+biz_id 或 warehouse_id+sku_id，created_at/id DESC | `idx_stock_flow_biz`、`idx_stock_flow_warehouse_sku_created` | 常见审计回查；任意多条件组合不保证都全索引覆盖。 |
| `StockAlertMapper.list` | status、可选 warehouse_id/sku_id；triggered_at/id DESC | `idx_stock_alert_status_triggered`、`idx_stock_alert_warehouse_status`、`idx_stock_alert_sku_status` | 按告警状态分页与按仓/SKU 筛选。 |

## 15. 面试最值得讲的 5 个难点

1. 三量库存不变量与有条件的 SQL 扣减。
2. 单据行锁、状态机和重复请求的副作用幂等。
3. 多 SKU 整单事务回滚。
4. 调拨在途量及盘点快照冲突。
5. Redis 提交后失效与旧读回填问题，以及为什么不把扣库存迁到 Redis。
