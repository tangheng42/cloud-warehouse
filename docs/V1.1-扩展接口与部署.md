# V1.1 向后兼容扩展

V1 的 50 个 operation、路径、HTTP 方法与 JSON 请求体不变。本页只说明可选请求头和可选通知接口；原始 `yuncang-openapi.yaml` 仍作为 V1 契约。

## 创建请求幂等

先执行 `docs/sql/04-v1_1-idempotency.sql`。以下四个原有创建接口可携带请求头 `Idempotency-Key`：

| 接口 | 操作域 |
|---|---|
| `POST /api/v1/inbounds` | `INBOUND_CREATE` |
| `POST /api/v1/outbounds` | `OUTBOUND_CREATE` |
| `POST /api/v1/transfers` | `TRANSFER_CREATE` |
| `POST /api/v1/stocktakes` | `STOCKTAKE_CREATE` |

键长 1～128，仅允许 ASCII 字母、数字、点、下划线、冒号、横线。同一用户、操作域、键首次创建成功时，键、请求体 SHA-256 摘要、业务单 ID 同事务提交。相同请求重试返回同一单据的**当前详情**，HTTP 仍为 201；改请求体时返回 409 `IDEMPOTENCY_KEY_CONFLICT`。首次业务失败则键与单据一起回滚，可原键重试。未传键时沿用 V1 建单语义，客户端自行承担网络重试重复建单风险。动作接口继续由状态机、行锁和条件更新防止重复库存副作用。

## 异步通知中心

先执行 `docs/sql/05-v1_1-notifications.sql`，再配置 `NOTIFICATIONS_ENABLED=true` 和 RabbitMQ 连接环境变量。默认关闭时无 MQ 连接要求。开启后提供：

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| GET | `/api/v1.1/notifications?page=1&size=20` | ADMIN、WAREHOUSE_MANAGER | 共享预警通知列表，按创建时间倒序；沿用 Bearer JWT 和 `ApiResponse<PageResult<NotificationVO>>` |

通知字段：`id, eventId, warehouseId, skuId, alertId, type, title, content, status, createdAt`。`type` 为 `LOW_STOCK` 或 `STOCK_RECOVERED`；当前是共享通知列表，`status` 固定初值 `UNREAD`，尚无个人已读能力。项目现有权限模型没有仓库级授权，因此仓库经理可见全部仓库通知；若以后添加仓库级权限，必须同步收紧此接口。

库存事务只同步写 `stock_alert`，状态变化时同事务插入 Outbox。独立发布器每 5 秒扫描到期 PENDING 行，使用 `FOR UPDATE SKIP LOCKED` 避免多个实例抢同一行，收到 Confirm 且无 Return 后标记 SENT。连接失败、Nack、不可路由则保留 PENDING，5 秒后重试。消费者数据库插入成功才由容器确认；`notification.event_id` 唯一键避免重复通知。消费异常不重排，消息进入 `<queue>.dlq`，需人工排查、修复并重投。

启动前设置 `RABBITMQ_HOST`、`RABBITMQ_PORT`、`RABBITMQ_USERNAME`、`RABBITMQ_PASSWORD`。可通过 `NOTIFICATIONS_EXCHANGE`、`NOTIFICATIONS_QUEUE` 指定独立命名空间。Redis 缓存单独由 `STOCK_CACHE_ENABLED` 控制，两者不影响库存 MySQL 事务的正确性。
