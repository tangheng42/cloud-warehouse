# 通知微服务环境变量排查

## 本次原因

学习接口的 RemoteNotificationQueryService 读取 `app.internal.token`，缺失时使用空字符串，因此在发起 Feign 请求前就抛出“未配置通知服务内部调用凭据”。通知服务的 InternalNotificationController 也读取同一配置，并校验请求头 `X-Internal-Token`。

本次检查时，IDEA 的 CloudWarehouseApplication 只设置了 DB_PASSWORD、JWT_SECRET、SPRING_PROFILES_ACTIVE；NotificationApplication 没有设置内部凭据。当前诊断进程和 Windows 用户环境也没有 APP_INTERNAL_TOKEN。

## 修复

两个服务的 application.yml 明确配置：

```yaml
app:
  internal:
    token: ${APP_INTERNAL_TOKEN:}
```

在 IDEA → Run → Edit Configurations 中，分别选择 CloudWarehouseApplication 和 NotificationApplication，在 Environment variables 中设置 `APP_INTERNAL_TOKEN`，两个值必须完全相同。保留主服务已有的数据库、JWT 和 profile 配置。使用随机生成的本地凭据，不要提交真实值。

本次已把同一个随机凭据写入本机 `.idea/workspace.xml` 的这两个运行配置；该文件被 Git 忽略。若 IDEA 正打开项目且尚未刷新磁盘修改，请检查运行配置是否已显示 APP_INTERNAL_TOKEN；若未显示，重新打开项目后再检查。

停止并重新启动两个服务后再请求学习接口。已经运行的 Java 进程不会因为文件修改而自动取得新的启动环境变量。

如果改用终端启动，在启动 Java/Maven 的那个终端中设置 `$env:APP_INTERNAL_TOKEN`；两个服务需使用相同的值。仅把变量写入项目根目录的 `.env` 不会自动传给 IDEA 启动的 Java 进程；本项目的 `.env` 用于 Docker Compose，未配置 Java 的 dotenv 加载。

## 如何判断下一步

- 仍提示凭据未配置：检查是否启动了正确的运行配置，以及是否重启主服务。
- 通知服务返回 401：检查通知服务是否也重启，以及两个凭据是否完全一致。
- 报找不到服务实例或连接失败：检查 Nacos 和通知服务注册状态，这与凭据缺失是不同的问题。
- 成功返回 `demo: true` 和 `records`：演示通知调用成功。

这里的内部凭据与 JWT_SECRET 用途不同：JWT 用于用户登录认证，APP_INTERNAL_TOKEN 用于主服务调用通知服务。NOTIFICATIONS_ENABLED 控制原有 RabbitMQ 通知功能，不能替代学习接口的内部凭据。
